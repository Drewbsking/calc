# MDOT TTC Typical Selector

The Work Zones card opens `calculators/mdot-ttc/`. Users browse all individual MDOT construction, maintenance, and survey traffic typicals, keep a separate project selection, download an editable Word table for Maintenance of Traffic (MOT), combine selected MDOT typicals into one PDF for GI and the preliminary spec book, or package individual PDFs in a ZIP for final submittal to MDOT Specs and Estimates. The tool uses the existing static site and makes no runtime requests to MDOT for exports.

## Catalog sources and meaning

The catalog contains **136 individual typicals: 88 construction, 32 maintenance, and 16 survey**. Membership comes from all three official MDOT PDF catalogs, so future refreshes include newly listed typicals even when the workbook has no corresponding row. Combined sets, CAD files, and sign-calculation spreadsheets are excluded to avoid duplicate details and non-PDF documents.

**Sheet1** of `MDOT TTC Typ Cheat Sheet.xlsx` supplies titles, classifications, notes, and maintenance relationships for its original 82 construction typicals and 15 maintenance alternatives. The workbook is read by worksheet name, not worksheet file order. Totals, sign quantities, saved usage counts, saved project selections, and the “DID NOT REVIEW” placeholder are not imported.

Cards, search, and exports use the descriptive MDOT catalog title for each typical. When MDOT lists only a filename, `DOCUMENT_TITLES` supplies its verified PDF drawing title; a newly listed filename-only typical requires title review before refresh can replace the catalog. `titleSource` records which MDOT source supplied the title. The original workbook title remains in `workbookTitle`, notes remain in `notes`, and workbook classifications remain in `filters`; the archived workbook is intact. Missing workbook classifications are “Unspecified.” Only case and whitespace variants are combined in those source fields. Original lane labels such as “2+,” and “4 or 5” appear as Workbook lanes tags; a plain count already represented by an existing-lane total is shown once. A maintenance sister is a related choice, not an automatic replacement or a recipient of the construction typical's RCOC classification.

The requested exception is typicals **105–107**: their imported workbook Roadway type is cleared to Unspecified and their workbook notes are removed. This removes the “Notes - Special” classification and workbook-note callouts from these three cards and their search text. The importer reapplies this cleanup on refresh. Typical **311** also corrects the erroneous workbook control label from Crush and Shape to Crossover during import. The archived Excel workbook and stored MDOT PDFs remain intact.

The four filter sections are **Typical category** (Construction, Highway Maintenance, Notes, or Survey), **Typical series**, **MDOT code**, and **Work activity**, in that order. There is no More filters section. Clear filters clears all four groups; Reset project restores the Construction category default and clears the other groups. Both collapse Possible matches.

**Typical series** follows the numbered groups in MDOT's `100-GEN-KEY`, from 100 — General notes through 360 — Rolling roadblock, plus 4000 — Maintenance and 5000 — Survey. It also includes 380 — Emergency pull-off signing, present in the current library but absent from that key. Construction groups cover their ten-number series (160 includes 160–169); maintenance and survey cover 4000–4999 and 5000–5999, including A/B variants and maintenance files without an M code. Groups follow numbers rather than titles: 302–304 remain in 300 — Advance warnings. Unrecognized series appear as Unspecified rather than inheriting the previous numbered group. Multiple series combine with OR, other fields/search combine with AND, and facet counts ignore their own group. Known series conflicts never become Possible matches. Required 100–104 remain excluded from browsing and counts, so the 100 option currently contains only 105–107. Filtering never changes the project selection.

**MDOT code** matches codes anywhere after the typical number, including later and compound segments. For example, `160-INT-LD-CLT-MID` matches INT, LD, CLT, and MID; `4110A-M-TR-NFW-2L` matches M, TR, NFW, and L. Numbered variants share a base code: 1LC/2LC/(1-2)LC use LC, CLT(7) uses CLT, GORE(4) uses GORE, and 2(R)SHIFT supplies SHIFT and (R). Parenthesized directions stay distinct from lane-count L: 2L does not match (L). A direction can describe a closure or shift; code filtering never changes verified work-activity or roadway classifications. LC includes 0LC notation, which does not establish a lane closure.

The code filter currently offers **50 choices** across the 131 optional details. Each code has a plain-language label in the filter. Codes are already visible in each card's full typical identifier, so they are not repeated as tags. Matching is case-insensitive and uses complete parsed codes, so FW does not match NFW. Duplicate occurrences count once per detail. Multiple code choices combine with OR, other fields/search combine with AND, and live counts ignore their own group's choices. Known code conflicts exclude Possible matches. The typical number, its A/B suffix, the PDF extension, and standalone numeric modifiers are not code choices; 2MILE remains a distance code. New unfamiliar codes remain available as written rather than being silently dropped. Required-only codes such as KEY remain in the full identifiers but are excluded from browse choices and counts. Category/default selection rules, saved selections, source classifications, and exports remain unchanged.

**Roadway type** is shown on detail cards and remains searchable; it is not a filter and has no facet counts. Tags retain Undivided, Divided, Freeway, All roadway types, and Unspecified as applicable. Undivided roads have no median or barrier separating opposing traffic (a center turn lane remains undivided); divided roads separate opposing traffic; freeways control access through entrance and exit ramps. Freeway and Divided can overlap, consistent with [MDOT's road definitions](https://www.michigan.gov/mdot/About/mdot-road-terms-and-definitions). Each applicable roadway tag is retained. A removed roadway criterion is ignored by filtering and cannot create a Possible match.

`roadway_classifications()` uses the descriptive MDOT catalog title, then a verified PDF title when MDOT lists only the filename, and finally an explicit workbook roadway label. Two- or three-lane, two-way roadway titles establish Undivided applicability, including maintenance and survey typicals previously left Unspecified. Typical 5401 matches all three types because its title and diagrams cover two-lane/two-way and divided/freeway roadways. Bare lane counts, two-way traffic alone, ramps, crossovers, and filename codes do not establish a roadway type. Non-freeway wording never supplies a Freeway match. Unclear applicability stays Unspecified, with an explanation to review the detail. These derived labels leave original workbook classifications intact and are regenerated on refresh.

General construction typicals **100–104** retain their **All roadway types** classification and original workbook values. They are required in every project, regardless of category or roadway. `selectable()` excludes these five records from search, available results, Possible matches, filter options, and filter counts. The complete catalog still contains 136 records; browsing covers the other 131 (80 Construction, 32 Highway Maintenance, 3 Notes, and 16 Survey). GEN remains a code choice for the three optional general typicals 105–107.

**Work activity** keeps one filter with these ordered choices: **Close the right lane**, **Close the left lane**, **Close the center turn lane**, **Close multiple lanes**, **Lane closure — side unspecified**, **Shift traffic**, **Shoulder / roadside work**, **Ramp work / closures**, **Intersection work**, **Mobile work / rolling roadblocks**, **Crossing / crossover work**, **Traffic control / signing**, and **Other work**. The same derived labels drive card tags, search, matches, and live counts. OR within this filter and AND across other filters remain unchanged; overlapping activities never duplicate a result.

`workTaskInfo()` in `core.js` uses existing classifications and descriptive MDOT titles, falling back to the verified PDF title for filename-only listings. Right/left follows traffic direction. Center-turn closures require explicit center-turn or CLTL wording; center-of-road work is not a turn-lane closure. Multiple-lane closures require explicit counts or multiple affected lane positions. Established lane closures with no classified side get **Lane closure — side unspecified**, including multi-lane closures whose side is unknown, and remain **Possible matches** for uncertain right/left/center choices. A shift direction never establishes a closure direction, and a parking-lane closure is not a verified right/left travel-lane closure.

Shoulder / roadside work includes work outside the shoulder. Ramp work / closures includes closures, treatments, and operations, including details whose descriptive title identifies ramp work. Shifts, intersection work, mobile operations, rolling roadblocks, crossovers, and haul crossings use their existing arrangement/work-area classifications. Traffic control / signing covers Notes-category general typicals, temporary traffic signals, and standalone extended lead-in, stopped-traffic advisory, and emergency pull-off signing typicals. Incidental speed reductions or advance-warning language in a lane-closure title do not create a signing activity. Known signing-only typicals do not become possible lane-closure matches.

All **131 optional details** have an activity. **Other work contains only 320, 5182A, and 5182B**: crushed-and-shaped surfaces and center-of-road survey work. This keeps the list compact while the detailed titles, classifications, and drawings remain available. Future unmatched activities stay reviewable under Other work. Required typicals 100–104 have Traffic control / signing tags but remain excluded from browsing and filter counts. These browsing changes do not modify source classifications, the catalog schema, saved selections, or exports.

The underlying fields in `classifications` still separate **Roadway type**, **Traffic arrangement**, **Work area**, and **Control method**. The Arrangement tag is omitted from cards because its closure, shift, crossover, and similar meanings overlap the visible Work activity tags. The underlying arrangement remains available to derive Work activity and search the catalog. Roadway types are Divided, Undivided, and Freeway; arrangements include crossovers, closures, shifts, merges, and rolling roadblocks; methods include traffic regulators, temporary signals, and AFADs. `classify()` in the refresh script derives these only from explicit workbook labels and MDOT titles. Filename abbreviations, notes about other typicals, and related typicals are not used to infer classifications. Unknown values remain Unspecified. These are browsing categories, not additional MDOT classifications.

A record can have multiple values: a freeway/divided-roadway detail with a closure and shift appears under both roadway types and both arrangements. OR within a field and AND across fields still apply, with no duplicate results; option counts can overlap. Intersection stays a Work area, while Crossovers, Single Shift, and Crush and Shape are removed from Work area. Notes, Signal Work, and Crush and Shape are not control methods. Original workbook values appear directly in the shared tag area when they add information. Typical 311 uses the corrected Crossover classification; its incorrect Crush and Shape workbook label is excluded from tags and search. Other source differences retain an explicit workbook label. Refreshes regenerate the browsing categories without changing the workbook, original labels, titles, notes, RCOC usage, or paint flags.

Typical category uses the display labels Construction, Highway Maintenance, Notes, and Survey while preserving the original workbook values. **Notes** contains every record whose first filename code is GEN, currently typicals 100–107. These records show Notes tags and are excluded from the Construction browsing category. Required typicals 100–104 stay in Always included, so the Notes filter count covers only optional typicals 105–107. This grouping also applies to future GEN typicals without changing their MDOT source family, identifiers, or saved selections. The catalog header reports these displayed categories (80 Construction, 32 Highway Maintenance, 8 Notes, 16 Survey); the stored MDOT source-family counts remain 88 construction, 32 maintenance, and 16 survey. For other typicals absent from the workbook, category comes from the MDOT source family; all other original workbook classifications, including RCOC usage and paint, remain “Unspecified.” Their cards identify missing workbook classifications with a tag, while explicit titles can supply the browsing categories above. Six filename-only catalog entries (100, 302, 303, 304, 4180, and 4204) use titles verified from the PDF title blocks, recorded in `DOCUMENT_TITLES` in the importer. Descriptive MDOT catalog titles take precedence if MDOT adds them later.

**Existing lanes** remains on detail cards and is searchable, but is not a filter. It describes the road before work; closure counts remain separate card information. Existing counts are labeled as totals across both directions (including a center turn lane where present), counts in the affected direction, or counts on the ramp. `lane_classifications()` uses the descriptive MDOT catalog title or verified PDF title for filename-only listings. Exact workbook counts can fill missing totals for explicitly undivided roads. Mixed labels and `+` values are preserved as source text, not interpreted as applicability ranges. For example, 123 uses MDOT's four-lane title while retaining the workbook's “4 or 5”; 202 uses three lanes in the affected direction while retaining “1+.”

The filter order is **Typical category → Typical series → MDOT code → Work activity**, with every filter optional. All choices keep their live result counts, including zero counts. Roadway type and lane counts remain visible on cards so users can compare details without extra filters.

Closed-lane counts are separate from road size and shift counts, and include center turn lanes when explicitly closed. Cards omit a redundant “Closed: 1 lane” badge when a directional Work activity already names a single-lane closure; exact counts remain visible for unspecified sides and multiple-lane closures. Staged closures such as 202 retain both one- and two-lane counts on the card and match Close multiple lanes without duplicating the typical. Parking-only and ramp-only closures are identified separately. Shoulder closures and work outside the shoulder show “No lane closure”; unspecified counts are never treated as zero. A shift, temporary signal, unnumbered group of lanes, or mobile operation alone does not establish the number closed. Shoulder references, including work outside the shoulder, supply the Shoulder / roadside work task rather than lane-count labels. These are descriptive browsing categories; the original detail and workbook references remain available on every card.

**Lane position** remains internal classification data; the standalone **Lane** tag is removed. The visible **Work activity** tags describe closures and shifts. `lane_positions()` uses descriptive MDOT titles, then specific drawing reviews in `DRAWING_LANE_POSITIONS`. Workbook work-area text, filename codes, and shift direction do not establish a closure side. Reviewed positions are bound to the PDF checksum and applied after download validation during refresh; changed PDFs fall back to their descriptive titles until reviewed again. Typicals 131 and 132 have left/center and right/center closures respectively; 202 and 206 retain their reviewed left closures. Typical 110 uses side unspecified and remains a Possible match for directional closure searches. Shift-only and signing-only typicals do not become directional lane closures. Multiple positions can supply multiple activities without duplicate results. Extra original work-area information appears in Andy's note unless visible activity/count tags already cover it; hidden lane-position data cannot suppress the note.

**Conditions noted by MDOT** appears on cards, related maintenance alternatives, and selected details. The repeatable `applicability_conditions()` importer extracts explicit duration, speed, traffic volume, sight distance, distance-from-vehicle, curb, reduced-width, advance-warning, and ramp-flow phrases from MDOT titles (or verified PDF titles when the listing is filename-only). It preserves qualifiers such as less than, longer than, maximum reduction, and or less; no speed thresholds or eligibility ranges are inferred. Empty conditions mean none were extracted from the title, not that the PDF has no additional requirements. Conditions remain visible information rather than filters, and the source PDF stays available for review.

The workbook's paint-quantity column supplies flags rather than a filter. “Yes” shows **Paint required** and “Maybe” shows **Paint may be required** on the typical and in the selected-details list. A reminder above the download buttons summarizes flagged selections and updates when details are added, removed, restored, or reset. “No” and “Unspecified” do not trigger a warning; missing values are not treated as a confirmed “No.”

PDF identifiers, URLs, and update dates are verified against the [MDOT construction catalog](https://mdotjboss.state.mi.us/TSSD/getSubCategoryDocuments.htm?category=Work+Zones&prjNumber=1403892&subCategory=Maintaining+Traffic+Typicals+), [maintenance catalog](https://mdotjboss.state.mi.us/TSSD/getSubCategoryDocuments.htm?category=Work+Zones&prjNumber=2173385&subCategory=Maintenance+Maintaining+Traffic+Typicals+), and [survey catalog](https://mdotjboss.state.mi.us/TSSD/getSubCategoryDocuments.htm?category=Work+Zones&prjNumber=2173386&subCategory=Survey+Maintaining+Traffic+Typicals+). Matching uses the unique typical number within its document family. For example, workbook 101 is mapped to `101-GEN-SPACING-CHARTS`, correcting its workbook hyperlink to 102. Codes with spacing or suffix discrepancies use the verified MDOT filename; literal plus signs in filenames are URL-encoded correctly.

`catalog.json` records the source workbook checksum, verification time, provenance rows, source URL and title, MDOT update date, PDF byte count, page count, and SHA-256 checksum. PDFs are stored under immutable checksum filenames. Source pages are copied without rasterization, resizing, or rotation changes. The downloaded packet adds a title page, index, and page-number labels; stored source PDFs stay intact.

## Refreshing the stored documents

The original `MDOT TTC Typ Cheat Sheet.xlsx` remains in the repository root. **Original Excel workbook (.xlsx)** beside the MDOT source library link downloads that preserved source file. Its checksum matches the workbook provenance recorded in `catalog.json`.

Use Python 3.10 or later with `pypdf` installed. From the repository root:

```powershell
py -3.13 calculators/mdot-ttc/update_catalog.py
```

An alternate workbook or output directory can be supplied with `--workbook` and `--output`. Review the changed catalog and run the checks below before publishing through the site's existing deployment process. Refresh is manual; the displayed verification date describes the stored snapshot, not a live check on MDOT.

The script validates the expected workbook headers, resolves every workbook reference, imports every individual PDF from all three MDOT listings, downloads PDFs into a temporary directory, checks signatures and page geometry, and only then promotes the files. It records the official family counts and replaces the catalog last, atomically. Missing catalogs or PDF links, ambiguous identifiers, invalid responses, and interrupted promotion cannot switch the active catalog to an incomplete set. Older PDF files are retained because an open browser may still reference an earlier catalog. The source workbook is never edited.

If an identifier in the previous stored catalog disappears from MDOT, refresh stops with the affected IDs. After confirming an official withdrawal, `--allow-removals` permits that change. Workbook references to withdrawn typicals must still be resolved in the workbook before refreshing.

## Project and export behavior

Detail cards show tags for **Typical category**, **Typical series**, and **Work activity**, followed by **Roadway type**. **MDOT code** remains a filter but is omitted from tags because the full identifier already shows the codes. Tags use the same values and series descriptions as the filter choices, with a separate tag for each applicable value and an explicit Unspecified tag for missing classifications. Roadway tags are retained independently of the filter list; required general typicals retain All roadway types. Available, Possible matches, Selected, and Always included cards use the same tag rendering. Existing lane/control information, RCOC usage, and paint flags remain visible after these tags. The original workbook classification dropdown is removed. Additional source values appear as Workbook road type, Workbook control, and Workbook lanes tags. There is no Workbook work area tag: unique work-area information is appended to Andy's note, preserving existing note text. Matching values are consolidated ignoring case and whitespace; a plain lane count already displayed as a total is not repeated, and Intersection is covered by Intersection work. Differing or more specific tag values retain the original wording and workbook label. The note keeps work-area fractions, mixed areas, shoulder sides, and lane counts not already established on the card. Simple lane count/side descriptions, intersections, shoulders, and crossovers already covered by tags are not repeated. Work-area text already present in a note or another workbook tag is not appended again. Missing-workbook information is also a tag. Andy's note remains one callout and retains DO NOT USE warning styling. MDOT conditions keep their existing presentation; original catalog values, filters, and exports are unchanged.

The **MDOT typical filename legend** sits between the filters and the Available/Selected panes and starts collapsed. It explains the entire filename: typical number, family/roadway codes, lane counts, positions, control methods, work and duration suffixes, and A/B variants. It includes worked examples for `152-CLT(7)-3(1R+2L)LC-2(L)SHIFT.pdf` and `160-INT-LD-CLT-MID`. Definitions come from MDOT's `100-GEN-KEY` and individual drawing titles; the source control previews typical 100 inside the page. A/B suffixes are described as typical-specific variants, not assigned a universal meaning. The legend is reference material and does not change filtering or project selections.

Every detail card has **Preview drawing**, including selected details, Always typicals, and Possible matches. Related maintenance alternatives have their own **Preview alternative** control. Click/tap the button, or activate it with Enter/Space, to open the panel. Hovering does not open or load a preview. **Previous/Next** visits every PDF page; **Zoom** offers Fit page and 150–300% of that fitted size, with scrolling for larger drawings. Close, Esc, or clicking outside dismisses the preview without changing the selection. Keyboard dismissal returns focus to the preview button. The panel stays inside the viewport and opens no browser window or tab.

`preview.js` loads the local PDF.js renderer and the requested stored PDF only when a preview is requested. It renders the actual PDF pages to a canvas, preserving their proportions and orientation, so refreshed PDFs need no separately generated thumbnails. Closing or switching previews cancels the old rendering task and releases its PDF/worker resources; stale responses cannot replace the current drawing. Failed or corrupt files identify the affected typical and offer **Retry preview**. The original View PDF link remains available. Previewing does not add cards or change downloads.

Filters sit above two independently scrolling panes: **Available details** on the left and **Selected details** on the right. Check cards to mark them, then use **Add marked →** or **← Remove marked** between the panes; each card also has an arrow for moving it individually. Marking alone does not change the project or its downloads. Both panes retain each detail's title, notes, flags, conditions, PDF links, and workbook classifications. Downloads and the project name are below the panes. On narrow screens the panes stack, with down/up transfer arrows between them.

Added cards leave the available pane. Removed cards return if they match the active filters. Available counts exclude optional details already in the report; filter counts still include them. Required typicals 100–104 are excluded from both. **Select all** in the available pane marks remaining exact matches; **Add marked** adds them. Possible matches require explicit review and marking. The selected pane’s **Select all** and **Remove marked** affect only user-added details, never the five required typicals. Checkboxes retain their checked, mixed, and disabled states. Marks are temporary and are cleared when their cards leave available results; project choices are saved independently. Selected and mobile totals include the five required typicals.

New and reset projects contain required typicals **100–104**, with no optional details chosen. **Construction** is the default category and shows 80 optional construction typicals; Notes is not preselected. The category group starts expanded; the note explains RCOC construction projects use these speed-reduction provisions. **Clear filters** clears search and all groups to browse the 131 optional records, without changing the report. **Reset project** clears the name and optional choices, restores the Construction category, and collapses Always included; it preserves the five required typicals. Optional IDs and the project name are saved under `mdot-ttc-project-v1`. Older saved selections containing 100–104 are normalized into the required group without duplication or a missing-record warning. Removing every optional choice and reloading still leaves those five typicals. Storage failures leave the tool usable in memory with a visible message.

Filter options display live matching counts for optional details, including search and all other filter groups while ignoring their own group’s choices. Required typicals 100–104 never contribute to the counts. Zero-count options remain visible and selectable, and checked options can always be removed. Counts update without closing groups or moving keyboard focus. Adding an optional detail to the project does not change its filter counts.

**Possible matches — review detail** keeps potentially applicable typicals accessible when a selected classification is Unspecified. `possibleMatches()` requires the search and category to match and rejects every known conflict with an active filter. It lists only records missing at least one selected classification, with those fields named on the card. For example, construction typical 205 appears here for MDOT code FW + Close the right lane because its closure side is unspecified; the known left-only closure 204 does not. Missing roadway types and lane counts do not restrict results or make a detail a possible match. Choosing a task that is established on the record, such as Shoulder / roadside work for 205, makes it an ordinary filter match. Main and possible results are disjoint and naturally sorted. The separate section starts collapsed; users can review a PDF and add a possible match individually, or explicitly mark reviewed cards and use Add marked. **Select all**, the main result total, and facet counts continue using exact classification matches. Changing or clearing filters preserves selections, and possible matches use the same saved IDs and exports as any manually chosen detail.

RCOC usage remains a card tag. Yes tags are green and No tags are red, with the text retained; other RCOC values keep their neutral styling. Required inclusion is explicitly based on typical numbers **100–104**, independent of workbook RCOC values. These typicals always appear in the **Always included** disclosure in Selected details. It starts collapsed on page load and Reset project; users may expand it to read notes, preview drawings, or open the PDFs. There are no marking checkboxes or removal arrows for required typicals. Word, PDF, and ZIP use the same naturally sorted union and include each required typical exactly once, even when no optional detail is chosen. Catalog validation rejects a catalog missing any required typical, preventing an incomplete report.

Every export captures its full report before starting, including the Always typicals; PDF and ZIP exports also capture the project name. All formats use the same natural typical-number order. PDF and ZIP exports check each file's checksum and expected page count, abort the entire download on failure, and identify the affected typical. Retry uses the failed export format with the current selection and project name. A failed Always typical must be restored before the report can be downloaded.

The combined PDF is for GI and the preliminary spec book. The project name is required for PDF downloads and may contain up to 160 characters. The PDF begins with a letter-sized title page and an index listing each typical number, title, and packet page range. Index rows link to the first page of that detail. Index pages expand as needed and repeat their column headings. Continuous “Page X of Y” labels include the title and index, so references match a PDF viewer's page count. Number labels occupy the blank bottom margin on current MDOT typicals, leaving their dimensions and original artwork intact. Project names use the PDF's standard Helvetica font; unsupported characters produce a clear error instead of being silently dropped.

The three download buttons have matching dimensions and a description explaining each file's use. **Download Word table** is the sole table export, for Maintenance of Traffic (MOT). It creates a real OOXML `.docx` table with Typical Number and Title columns, repeating headers, explicit column widths, wrapped titles, and rows that do not split across pages. Word downloads do not require a project name. There is no clipboard, table preview, or manual-copy control. Exports are available for a report containing only the five required typicals; the combined PDF still requires a project name. Export buttons are disabled while a download is being prepared or the catalog is unavailable.

**Download ZIP package** is for final submittal to MDOT Specs and Estimates through ProjectWise. It packages one original PDF per report detail in a flat archive, using the official typical identifiers as filenames (for example, `110-TR-NFW-2L.pdf`). The PDF bytes are unchanged, without the combined packet's title page, index, or added page numbers. The ZIP uses the same selected details and automatic Always typicals as the Word table. To include the entire library, choose **Clear filters**, check **Select all**, use **Add marked**, then download the ZIP. A project name is optional: when present, it supplies a safe filename prefix; otherwise the archive is named `mdot-ttc-details.zip`. This is a local download for submission through your existing ProjectWise process.

The export libraries are stored locally in `vendor/`: **pdf-lib 1.17.1**, **docx 9.5.1**, and [**fflate 0.8.3**](https://github.com/101arrowz/fflate), with their MIT licenses. Drawing previews use the compatibility build of [**PDF.js 6.3.289**](https://github.com/mozilla/pdf.js/releases/tag/v6.3.289), with its Apache-2.0 license, worker, character maps, standard fonts, and image decoders stored in `vendor/pdfjs/`. Font/decoder licenses are included beside those files. The scripting sandbox is not included or enabled. `vendor/manifest.json` records the npm archive URLs, registry integrity hashes, and checksums for every local renderer asset as well as the export bundles. No CDN, package installation, or build step is needed to serve the selector.

## Validation

```powershell
node --test tests/*.test.cjs
py -3.13 -m unittest discover -s tests -p test_mdot_ttc_catalog.py
py -3.13 tests/mdot_ttc_browser.py
py -3.13 tests/mdot_ttc_zip_browser.py
py -3.13 tests/mdot_ttc_transfer_browser.py
py -3.13 tests/mdot_ttc_preview_browser.py
py -3.13 tests/calculator_routes_browser.py
```

Core checks cover filters, notes, defaults, project-name and selection persistence, immutable export selections, escaping, source checksums, PDF page geometry, rotated pages, and export failures. Importer tests simulate failed downloads, malformed PDFs, ambiguous catalog records, and a failed final promotion. Browser checks cover the real downloads, title and index content, index destinations, page numbers, storage failures, catalog loading failures, mobile layout, and hosting under `/calc/`. ZIP browser checks independently read the archive with Python's `zipfile`, compare every file byte for all 136 typicals, check report order and Word-table agreement, and exercise optional names, frozen exports, missing/corrupt files, and retry behavior. Transfer browser checks cover marking and individual moves in both directions, possible matches, automatic typicals, keyboard use, independent scrolling, mobile navigation, persistence, and export agreement under root and `/calc/` hosting. Preview browser checks render all 150 pages, check proportions and visible drawing content, verify that hovering does not load a preview, exercise click/keyboard/touch, page controls, zoom, selected/Always/related cards, failure/retry, cancellation, and lazy loading at root and `/calc/`. Generated QA files stay in the system temporary directory.
